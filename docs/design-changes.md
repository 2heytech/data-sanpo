# 設計の変更・補足記録

基本設計書 v1（2026-10-03。原本はこのリポジトリに置いていません）から、実装にあたって変更・具体化した点を記録します。
原本は変更せず、ここに「何を・なぜ」変えたかを残します。新しい変更は末尾に番号を足してください。

状態: **採用** = 実装済み / **提案** = 判断待ち（未実装）

## 1. 値なしの状態に `withheld`（サイト側で非表示）を追加 — 採用

- 設計書 8章: status は observed / estimated / derived / missing / suppressed / not_applicable。
- 変更: `withheld` を追加。町丁目の割合で、分母（例: 年齢判明人口）が指標ごとの下限
  （初期値 50人）未満のときに値を出さず、この状態にする。
- 理由: 人口数十人の町丁目では1人の違いで割合が数ポイント動き、地図上で極端な色になる。
  出典の「秘匿」（suppressed）とサイトの判断による非表示を区別しないと、出典が非公開に
  したように誤解される。下限は `pipeline/config/indicators.toml` の `min_denominator`。

## 2. 凡例の区切りは「指標・時点・粒度」ごとに固定 — 採用

- 設計書 4章: 「色域は同一指標・同一定義の比較で固定」。
- 変更: 粒度（区市町村／町丁目）も固定の単位に加え、粒度ごとに分位（5階級）で区切る。
  区切りは公開版の生成時に計算して `legend.json` に保存し、地図の移動では変えない。
- 理由: 人口や世帯数などの件数は粒度によって桁が違い、同じ区切りでは片方が単色になる。
  割合も、区市町村は値の幅が狭いため町丁目と同じ区切りでは差が見えにくい。

## 3. 島しょ部の表示範囲切替 — 採用

- 設計書: 対象は東京都全域だが、地図の初期範囲の記載なし。
- 変更: 初期表示は区部・多摩。地図左上の切替で伊豆諸島・小笠原諸島へ移動できる。
- 理由: 東京都全域（南鳥島まで）を一度に表示すると、区部が判別できないほど小さくなる。

## 4. 市区町村界は町丁目境界を合成して作る／水面調査区は除外 — 採用

- 設計書 4章: 統計と同じ基準の境界を e-Stat 統計GIS等から取得。
- 具体化: 区市町村の境界は、同じ版の町丁目境界を合成して作る。面積は町丁目の公表面積の合計。
  e-Stat 境界の水面調査区（HCODE=8154）は地域として扱わない。
- 理由: 別の出典の市区町村界を使うと、海岸線や境界の版が町丁目とずれる。人口密度の分母も
  同じ境界から作ることで、区市町村と町丁目の値の整合が取れる。

## 5. 区市町村の値は公表値を使い、町丁目の合計は検証に使う — 採用

- 設計書 5章: 「公表値がある場合は原数値と独自計算値を区別する」「町丁目の率を単純平均しない」。
- 具体化: 小地域集計に含まれる区市町村の行（表章単位1）の値をそのまま区市町村の値とする。
  町丁目の合計と区市町村の値が 0.5% 以上ずれたら検証で警告する。秘匿された町丁目の値は
  合算先に含まれているため、町丁目側では値なし（suppressed）として二重計上しない。

## 6. 地域ID の命名規則と9桁・11桁コードの対応 — 採用

- 設計書 7章: 内部IDと出典側コードを分け、対応表で管理する。
- 具体化:
  - 区市町村 `muni-{団体コード5桁}`、町丁目 `area-{KEY_CODE 11桁}`。出典側のコードとの対応は
    `source_keys` に保存。境界の変更で同じコードが別の範囲を指すようになったら、新しい内部IDを
    発行して対応表で旧IDと結ぶ。
  - 丁目に分かれない町・字は、境界の KEY_CODE が末尾 `00` の11桁、統計表では9桁になることがある。
    11桁の行を優先して結合し、9桁の行は対応する境界が空いている場合のみ使う。対応できなかった
    コードは取込時に件数を表示する。

## 7. 地域ページは区市町村から公開 — 採用

- 設計書 12章: 「単なる数値の複製ページを大量生成せず、内容が整った地域から公開する」。
- 具体化: 初期は区市町村（62ページ）のみ生成する。主な指標・都内の順位・となりの区市町村との
  比較・データの読み方・出典を載せる。町丁目（約5,000地域）は地図で閲覧でき、ページ化は
  解説が書けるものから追加する。
- あわせて、指標ページにも区市町村別の一覧表を載せ、地図を開かなくても内容が分かるようにした。

## 8. 共有URLには地図の中心座標も含めない — 採用

- 設計書 3章: 「指標・年度・地域IDをURLに保存。自宅等の精密な座標は初期共有URLに含めない」。
- 具体化: `?i=指標&p=時点&a=地域ID` のみ。地図の中心・ズームも保存しない（拡大した位置が
  自宅付近を示すことがあるため）。地域を選んでいれば、開いたときにその地域へ移動する。

## 9. 公開版は上書きしない／DBスナップショットを同じ版で保存 — 採用

- 設計書 10章「保存と復旧」の具体化。`python -m tdm export` は既存の release_id を上書きせず
  エラーにする。生成時に管理用DBのコピーを `data/releases/{release_id}.sqlite` に残す。
  `manifest.json` に全ファイルの sha256 と git commit を記録する。

## 10. DB制約で「値なしをゼロにしない」を強制 — 採用

- 設計書 7章「制約と索引」の具体化。`observations` に
  「status が値なし系 ⇔ value が NULL」の CHECK 制約、`locations` に日本の範囲の座標 CHECK を設定。
  取込コードの誤りで欠測が 0 になることを DB 側で防ぐ。
- 注意: e-Stat の記号「-」は「該当数値なし」（真のゼロ）として 0 にする。「X」は秘匿。

## 11. 開発用の架空データ（fixture） — 採用

- 実在しない団体コード（13199・13299・13499）と架空の地名で、e-Stat と同じファイル形式の
  データを生成し、本番と同じ取込→検証→公開ファイル生成→サイトビルドを CI で通す。
  架空データで表示している間は、全ページ上部に「架空データ」と表示する。
- 理由: 行政サイトへ接続できない環境（CI 等）でも、秘匿・少人数・9桁コード・水面などの
  例外処理を毎回検証できる。

## 12. 検索の表記ゆれの吸収 — 採用

  漢数字／算用数字の丁目（「一丁目」と「1丁目」）、「ヶ・ケ・が」（霞ヶ関／霞が関）を同一視する。

## 14. 犯罪の人口当たり件数に昼間人口の分母を併記（旧提案P1） — 採用（#28 で実装）

- 設計書 5章: 認知件数と人口当たり件数。住民人口で割った値は被害確率ではないと注記。
- 変更: 区市町村では「住民1,000人当たり」と「昼間人口1,000人当たり」を並べて表示する。
  昼間人口は国勢調査の従業地・通学地集計（区市町村単位）を使う。町丁目には昼間人口の公表値が
  ないため、町丁目は件数と住民当たりの値のみとし、繁華街では件数を主に見せる。
- 理由: 千代田区・中央区などは住民人口が小さく、住民当たりの率が極端に高くなる。分母の違う
  2つの値を並べることで、率が人の出入りに左右されることが伝わる。
- 実装: 犯罪データを追加する段階2で、指標カタログに `denominator_indicator` を持たせて実装する。

## 15. 配信容量の測定と PMTiles 化の判断基準（旧提案P2） — 採用

- 設計書 9章: 1回の地域読み込みを圧縮後数MB以内、Workers の1ファイル上限 25MiB。
- 変更: 公開版の生成時に全ファイルの圧縮後サイズを `manifest.json` の `size` に記録し、
  次を超えたら警告する（1ファイル 25MiB 超は公開不可としてエラー）。
  - 初回表示（指標カタログ・地域一覧・区市町村境界・既定指標の値）: 圧縮後 1MB
  - 1区市町村の町丁目を開くとき（境界・地域一覧・値）: 圧縮後 3MB
- 実測（2026-10-03、令和2年国勢調査・東京都 5,596 町丁・字等）: 公開ファイル合計 9.8MB（圧縮後 1.8MB）、
  初回表示 166KB、最も重い区市町村の町丁目読み込み 103KB（いずれも圧縮後）。目安を大きく下回るため
  GeoJSON 分割のまま進める。
- 判断: 今後、実データで警告が出た場合に、該当区市町村の境界の簡略化を強めるか、町丁目境界を
  PMTiles（R2 配信）に切り替える。警告が出なければ GeoJSON 分割のまま進める。

## 16. 実データの取得を GitHub Actions で実行（旧提案P3） — 採用

- 設計書 10章: 初期は手動実行の Python 処理、安定後に定期実行。
- 変更: 手動実行のワークフロー「Data release」で、取得 → 検証 → 公開版生成 → サイトのビルド
  （→ 任意で Cloudflare へデプロイ）を行う。取得したファイルの一覧と CSV の先頭行をログに出し、
  列名を確認できるようにする。元データ・管理DB・公開版は private リポジトリの Artifacts に
  90日保存する（長期の保管先は別途決める）。
- 取得処理は、行政サイトが HTML（エラー画面）を返した場合や ZIP 内に不正なパスがある場合に失敗にする。
- 理由: 開発用のクラウド環境からは行政サイトに接続できないが、GitHub のランナーからは接続できる。
  取得と加工を同じ手順で再実行でき、設計書の「取得から公開までの処理を再実行可能にする」を満たす。
- 確認済み（2026-10-03）: GitHub Actions から e-Stat の一括ダウンロードで取得できる。

## 17. e-Stat 小地域集計の実ファイル形式への対応 — 採用

- 初回の取得で、当初の統計表ID（T001100・T001101）は地域メッシュ単位の表だったことが分かった。
  小地域（町丁・字等）の表は T001081（男女別人口総数及び世帯総数）、T001082（年齢5歳階級・4区分別人口）。
  ほかに T001083〜T001086（世帯人員・家族類型・住宅の所有・建て方）も小地域で取得できる。
- 秘匿処理の記号は HTKSYORI=2 が「秘匿され合算先に含まれる地域」（HTKSAKI に合算先の6桁）、
  HTKSYORI=1 が「秘匿地域の値を含む合算先」（GASSAN に一覧）。当初の想定と逆だったため修正した。
  人口総数・世帯総数の表には秘匿がなく、年齢の表には秘匿（125地域）がある。
- 年齢の表には年齢不詳の列がないため、割合の分母は「15歳未満＋15〜64歳＋65歳以上」（年齢判明人口）とした。
- 取込結果: 境界 5,596 地域（水面調査区 42 を除外）、区市町村 62。統計の行 5,657 のうち境界に対応しないコードが 5。
  町丁目の合計と区市町村の公表値は全区市町村で一致（差 0.5% 未満）。

## 18. 公開前のプレビューを site-preview ブランチに置く — 採用

## 20. 2015年国勢調査を加え、時点のスライドバーで変化を追えるようにする — 採用

- 変更: 2015年（平成27年）国勢調査の小地域集計（T000848・T000849）と境界を取り込み、
  人口・世帯数・人口密度・年齢構成の割合を2時点で表示する。取り込む時点は `pipeline/config/censuses.toml` に古い順で並べ、
  地図の境界は最新の時点（2020年）を使う。2010年は統計GISの境界データを同じ方法で取得できなかったため見送った。
- 過去の時点の町丁・字等は、同じ地域コードで面積の差が5%以内の地域だけ2020年の境界に重ねる。
  それ以外（境界が変わった地域）は値を出さず、理由を注記する。2020年に新設された地域は2015年の値なしとする。
  元データより細かく割り振らない原則を守るため、按分による組み替えはしない。
- 人口密度は各時点の境界の面積で割る。
- 凡例の区切りは全時点の値をまとめた分位にした。時点ごとに区切りを変えると、同じ色でも値が変わり、
  スライドバーで色の変化を追う意味がなくなるため。
- 理由: 利用者の要望（時系列の変化をスライドバーで追いたい）。

## 21. 地図画面を「左: 条件、中央: 地図、右: 地域の情報」に再配置し、地名を表示 — 採用

- 理由: 利用者の要望。条件と結果の置き場所を分けると、操作と読み取りが混ざらない。

## 24. 区市町村の境界の内側に出る余計な線をなくす — 採用

- 変更: 区市町村の形は町丁・字等を合成して作るが、町丁・字等の間のわずかなすき間や、除外した水面調査区が
  穴として残り、選択時の赤い枠や境界線が区市町村の内側にも描かれていた（2020年の区市町村で穴が計4,777個）。
  合成時に約0.5m だけ膨らませて縮め戻してすき間を閉じ、残った穴は埋める。町丁・字等の形は変えない。
- 面積（人口密度の分母）は町丁・字等の公表面積の合計のままで、この処理の影響を受けない。
- 理由: 利用者の指摘（不要な赤い線が入っている）。

  左の「表示」に「地名の下に数値を表示」の切り替えを置く。
- 理由: 利用者の要望。

## 26. 指標「人口増加率」を追加する — 採用

- 変更: 前回の国勢調査（5年前）からの人口の増減率 =（今回 − 前回）÷ 前回 × 100 を、区市町村・町丁・字等で表示する。
  新しい種類 `change` として indicators.toml に定義し、分子（増減）と分母（前回の人口）を保存する。
- 2010年は前回（2005年）を取り込んでいないため時点に含めない（2015年・2020年の2時点）。
- 町丁・字等は、両方の時点で2020年と境界がほぼ同じ地域だけ計算する。秘匿処理の合算の扱いが両時点で異なる地域、
  前回の人口が50人未満の地域は値を出さない。
- 凡例は0（増減なし）を境にした発散配色（減少＝橙、増加＝紫）で、減少側・増加側をそれぞれ3等分する。
- 推移表では、増減率そのものが前回からの変化なので「前回から」の列を出さない。
- 理由: 利用者の要望。

## 27. 指標「1世帯あたり人数」を追加する — 採用

- 変更: 人口総数 ÷ 世帯総数 を、区市町村・町丁・字等の全時点（2010年・2015年・2020年）で表示する。
  分子・分母とも国勢調査の小地域集計の同じ表（人口・世帯）から取り、率は分子・分母から計算する。
- 施設等の世帯（寮・病院など）とその人数を含むため、国勢調査が公表する「一般世帯の1世帯当たり人員」とは一致しないことがある。

- 率の内訳の単位を指標ごとに持てるようにした（fraction_units、例: 人 ÷ 世帯）。割合の範囲チェック（0〜scale）は単位が % の指標だけに行う。

## 27-2. 最終学歴（段階2の最初の指標）を e-Stat「ファイル」の小地域集計CSVから取り込む — 採用

  - 「大学・大学院卒の割合」=（大学＋大学院）÷ 最終卒業学校が判明している卒業者 × 100。

## 28. 犯罪の認知件数（警視庁）と昼間人口を追加し、住民当たり・昼間人口当たりを並べる — 採用

- 出典:

  - 「昼間人口」も指標として加えた（分類「人口・世帯」、区市町村のみ）。

  件数・住民当たり・昼間人口当たりを並べる。指標名を押すとその指標に切り替わる。
  #14 で予定した `denominator_indicator` は、件数や人口など別の指標どうしの比として実装した（kind は ratio のまま）。
- 区市町村だけの指標（昼間人口・昼間人口当たり）は、拡大しても町丁目の色分けに切り替えず区市町村の色のまま表示する。
- 町丁目への対応付け: CSVには地域コードがなく「千代田区飯田橋１丁目」のような名称だけなので、区市町村名で分けたうえで
  町丁目名を境界の名称と照合する（全角数字・漢数字の丁目、ヶ／ケ／が を同一視。#12 と同じ考え方）。

  行がない区市町村（島しょなど）は、その年0件とする。
- 町丁目の住民当たりは、人口100人未満の地域を表示しない。丸の内・大手町などは住民がほとんどいないため率は出ず、件数で見る。

- 境界は2020年のものを使うため、2021年以降に新設・改称された町丁目は対応できず、区市町村の値にだけ含まれる。

  （境界の GST_NAME）。地域区分（region）は東京都は区部・多摩・島しょ、政令指定都市の区は市の名前。
- 配信（Cloudflare Workers 無料枠の1版2万ファイルに収めるため）:
  - 町丁・字等の値: 区市町村ごと → 都道府県ごと（values/<指標>/<時点>/<都道府県2桁>.json）。
    全国の指標×時点が約130あり、区市町村ごと（約1,900）だと数十万ファイルになる。
  - 区市町村界: 全国を粗く（約200m）1ファイル（初回表示）＋都道府県ごとに細かく（約30m、拡大したとき）。
  - 検索索引: 区市町村は全国で1ファイル、町丁・字等は都道府県ごと（search-index/<都道府県>.json）。
    地図では表示中（または選んだ地域）の都道府県の町丁・字等を探す。
  - areas.json に prefectures（都道府県の一覧と範囲）、municipalities に prefecture を加える。
    indicators.json の各指標に値のある都道府県（prefectures）を加え、東京都だけの指標はそう表示する。
  - 見込み: 町丁目の境界・地域一覧（区市町村ごと）約3,800＋値 約7,000＋ページ約2,000で約1万3千ファイル。
- ヘッダーの表示中の地域（#51）は、公開版の都道府県が1つならその名前、複数なら「全国」。
- 住民税（#50）も全国の区市町村に広げる。政令指定都市は総務省の表に市全体の行しかなく、区に割り振ると元データより
  細かくなるため、区には値を入れない（注意書きに明記）。
- 3つの粒度を縮尺で切り替える（2026-10-03 ユーザー追加依頼「都道府県レベル、市区町村レベル、町丁目レベルがシームレスに
  切り替えられるように」）: 地図を縮小（ズーム6.5未満）すると都道府県、拡大すると区市町村、さらに拡大（12以上）で町丁・字等の
  値で色分けする。凡例・一覧・順位も表示中の粒度に合わせる。
  - 都道府県の値は、区市町村の分子・分母（人数・件数は値）を合計して出す。値のない区市町村が1つでもある都道府県は値なし
    （欠けた分を0とみなさないため）。分子・分母のない平均などは都道府県の値を作らない。
  - 住民税は政令指定都市の区に値がないため、総務省の表の市町村の行（政令指定都市は市全体）を合計して都道府県の値にする。
  - 都道府県界は区市町村の形を合わせて作る（boundaries/<版>/prefectures.geojson、境のすき間や水面の穴と0.1km²未満の島を除いて約400mで簡略化。除かないと全国で圧縮後4MBになる）。
    値は values/<指標>/<時点>/prefectures.json。検索でも都道府県を選べ、選ぶと都道府県の範囲へ移動する。
  - 指標のページに都道府県別の値の表を加える。
- 順位: 都道府県は全国の中、区市町村は同じ都道府県の中、町丁・字等は同じ区市町村の中で数える。区市町村の一覧も都道府県ごと。

  （入力 prefectures で指定可）。都道府県ごとの元ファイルは Actions のキャッシュに残して e-Stat から取り直さない。

  局所的になる）、それ以外の索引は取込の最後に作る。キャッシュも大きくする（最初の全国実行は3時間を超えた）。

## 69. 管理用DBの観測値を番号で持ち、境界を WKB で持つ — 採用

- 何を: 管理用 SQLite の観測値の表（observations）を、文字列を番号にした表（obs、WITHOUT ROWID）と番号の対応表（keys）に分けた。
  地域コード・指標・期間・出典・状態・注記などの文字列は keys に1回だけ書き、obs には番号を書く。
  これまでの列名で読めるように、同じ名前のビュー observations を残したので、読む側（率の計算・検証・書き出し）は変えていない。
  書き込みは tdm.db.insert_observation だけで行い、期間の種類・状態・値の有無の確認（欠測を 0 にしない）はそこで行う。
  obs には外部キーの制約がないので、地域・出典・境界・指標の定義が揃っているかは検証（tdm.validate）で確かめる。
  町丁・字等の合計と区市町村の値の照合は、ビューどうしの JOIN だと全国で終わらなかったため、指標ごとに1回読んで Python で集計する。
  町丁目などの境界は GeoJSON の文字列ではなく WKB で持つ（座標の精度は変えない。古い DB の文字列も読める）。
- なぜ: 全国の管理用DBは約18GB になり、Actions のランナー（ディスク・メモリ）の限界に近く、保存して次の実行で使い回すこともできなかった。
  264万行の試算で1行 407→約100バイト、書き込み 55→34秒、東京都の fixture の DB は 6.1MB→1.4MB。書き出す公開用ファイルの中身は変わらない
  （出典のハッシュと取得日時を除く）。DB が小さくなれば Release に保存でき、変わらない出典の取込結果を使い回す次の段階に進める。
  ビュー経由の一括読みは表を直接読むより遅い（66万行で 0.3→2.7秒）ので、全国の書き出しで目立つようなら obs を直接読む形にする。

## 115. 地域ページの考察に駅・空港・港・地価公示・天気を加え、特徴を一言で表す題名を付ける — 採用（#113 の考察を変える）

- 何を:
  - 「データから考えられること」に、地図の点のデータを市区町村ごとにまとめた文を加える（`web/src/lib/placeStats.ts`）。
    点の値をそのまま使い、地域に割り振る推計はしない。値のない点は使わない（0 にしない）。点のない市区町村には出さない。
    - 空港: 市区町村にある空港の最新年の乗降客数（年1,000人以上のとき）。国際線が2割以上、または全国の空港の上位10%ならその旨を書く。
    - 港: 全国の港の上位半分に入る乗降人員のとき。
    - 駅: いちばん利用者の多い駅（同じ駅グループの事業者の値を同じ年度で合計）。全国の市区町村の上位30%なら考察、
      それ以外は駅の数と利用者数を事実として書く。
    - 地価公示（住宅地の地点だけ）: 地点の価格の中央値と、5年前と同じ地点の変化率の中央値（2地点以上）。
      全国の市区町村の上位5%（上がり方は +10%以上も条件）なら考察、それ以外は価格と変化を事実として書く。
      地価公示の住宅地の地点がない市区町村（約360）は、都道府県地価調査の住宅地の地点で価格と変化を事実だけ書く（調べ方・時点が違うので順位は付けない）。
    - 天気（気象庁の観測所の平年値）: 市区町村の中の観測所のうち、要素ごとに代表点に近いもの。降雪量（300cm以上で全国の観測所の上位20%）・
      日照時間（上位10%）・降水量（上位・下位10%）のうち目立つものを1つ。観測所の標高が500m以上なら高原や山あいのまちと書く。
      標高は観測所の標高だけを使う（地図の標高タイルは画面の重ね合わせだけで、市区町村の値はないため）。
  - 考察は最大8つにする（#113 では6つ）。全国順位の考察に、住み始めてからの年数（20年以上・5年未満）・中学校の1学級の生徒数・
    保育の利用率・投票率・外国人の延べ宿泊者数と割合を足す。
  - 「データで見る〇〇」の見出しのすぐ下に、特徴を一言で表す題名を出す（例「雪が多く、米どころのまち」「空港があり、借家に住む人の多いまち」）。
    表示する考察と、全国の上位・下位10%に入る指標の考察から、全国の中で目立つ順に、課題に当たらない言い回しを2つまで選んでつなぐ。
    言い回しは考察ごとに決めておく（`rankInsights.ts` の highTag・lowTag と、点のデータの考察）。
    題名の元になった考察はページの考察にも必ず入れる。ページの説明文（検索結果の説明）にも題名を入れる。
    住む人の国籍や外国人の割合は題名に使わない（考察の本文には残す）。住む人の出身でまちを言い表すことになり、偏見につながるおそれがあるため。
  - 課題に当たる文（人口減少・高齢化・空き家など）は1ページに3つまでにする。似た課題の文が並んで暗いページにならないようにするため。
  - 理由の書き方を、当てはまる地域に限る（#113 の考察を直す。学級の人数の文と同じく、因果を取り違えないため）。
    - 空き家率: 空き家には別荘や入居者を募集中の賃貸住宅も含むので、人口が減っていない市区町村（軽井沢町など）では
      「別荘や賃貸用の住宅など、ふだん人が住んでいない住宅が多い」と書き、「使われなくなった家が増えている」とは書かない。
      人口が減っている市区町村も、別荘などを含むことを書いたうえで「長く使われていない家も多い」とする。
    - 合計特殊出生率が低い方の「若い単身の人が多い都市部などで低くなりやすい」は、人口密度が全国の上位25%の市区町村だけに書く
      （山あいの町村などには当てはまらないため）。
  - 差別的な表現の再確認として、国籍別の外国人の割合の考察から理由の推測（「働く場や学ぶ場を通じたつながり」）を除き、
    「〇〇の人が比較的多く暮らしている地域のようです」だけにする。歴史的な経緯で暮らす人が多い地域などに当てはまらないため。
  - 実データ（2026-10-14 公開版）の全1,896市区町村で、題名のない市区町村 0、題名の種類 821。課題に当たる文だけのページ 0（課題の文は多くても3つ）、
    外国人の考察と犯罪の考察が同じページに並ぶもの 0。「治安」「貧」「低所得」「学歴」「危険」「問題」「かもしれません」などの語 0。
- なぜ: 2026-10-15 のユーザー依頼「ランキングだけではなく、その市区町村の駅、港、空港、や標高、地価、天気など、すべてのデータを見て、
  もう一度コメントを追加して欲しい／追加した後には改めて差別的な表現が入っていないか確認して／市区町村のデータコメントの冒頭に
  その特徴を一言で表す一文をタイトルにつけたい」。表の順位だけでは似た文の市区町村が多く、地図の点のデータを使うと
  その地域らしさ（空港・港・雪・地価の動きなど）が出せるため。

## 116. 地域ページの考察をテーマごとにまとめ、読む順に並べる — 採用（#113・#115 の考察の並びを変える）

- 何を:
  - 「データから考えられること」をテーマごとにまとめ、小見出し（気候と土地・交通・住む人・住まい・仕事と産業・子育てと学び・
    安全と健康・選挙）を付ける。広い画面では見出しを左、文を右に並べ、スマホでは見出しを上に置く。
  - テーマの並びは、題名の元になった考察のテーマを先頭に（題名のすぐ下で理由が分かるように）、あとは全国の中で目立つ考察のあるテーマから。
    課題に当たる文（人口減少・高齢化など）は目立ち方を割り引き、地域の特徴から読み始められるようにする。
    選挙（政党の得票率など）は、まちの第一印象が支持政党にならないよう最後の方にする。
  - テーマの中は、題名の元になった考察を先に、あとは話がつながる順にする（人口の増減 → 年齢 → 出生率 → 外国人 → 世帯、
    住み続ける年数 → 持ち家・借家 → 地価 → 空き家、空港 → 港 → 駅 → 通勤の手段 など）。
  - どの地域にも出やすい考察（昼と夜の人口がほぼ同じ、まちの外へ通う人がやや多い、全国の平均的な年齢構成に近い）は、
    ほかに考察が6つ以上あるときは出さない。同じことを言う考察（持ち家が少ない方の順位と、借家が多いという文）は1つにする。
- なぜ: 2026-10-15 のユーザー依頼「それぞれの市区町村別コメントについて、コメントの順番を練り直して。人口など、一般的な項目から
  言及していくか、興味深いものから言及していく感じでも良いので、全体として、読み手にとって興味深い文章になるように、工夫してください」。
  これまでは考察を出す処理の順（全国順位・空港・港・駅・天気…）で並べていたため、話題が行き来して読みにくかった。
  目立つ話題から入り、同じ話題をまとめて話がつながる順に読めるようにする。

- 何を: 比例代表の得票率（12政党）の指標ページの題名と説明文（検索結果に出る文）を変える（`web/src/lib/indicatorPage.ts`）。
  - 題名: 「比例代表の得票率（れいわ新選組）の市区町村ランキング（全国）」→「れいわ新選組の得票率 都道府県別・市区町村別ランキング（比例代表）」。
    都道府県別の表がないときは「都道府県別・」を付けず、市区町村の値がないときは「〇〇の得票率 都道府県別（比例代表）」にする。
  - 正式名に、よく使われる略称が含まれない政党だけ、題名に略称を使う（自由民主党→自民党、社会民主党→社民党）。
    説明文には「自由民主党（自民党）」と両方を書く。日本共産党・日本維新の会などは、正式名に「共産党」「維新」が含まれるのでそのまま。
  - 説明文: 「〇〇の比例代表の得票率を、都道府県別と全国の市区町村別のランキングで紹介（2024年10月 衆院選・2025年7月 参院選・2026年2月 衆院選）。」
    のように、その政党の値がある選挙を時点の順に並べる。
  - 見出し（h1）、パンくず・Dataset の名前、地図の指標名、indicators.toml の名前は変えない。選挙以外の指標の題名・説明文も変えない。
- なぜ: ユーザーの依頼（2026-10-17、検索に出やすくする方法の検討で、題名を直すかのカードに「直す」）。
  Search Console（10-06〜10-14）で表示回数がいちばん多いのは選挙の指標ページで、わかっている検索語は「れいわ新選組 得票率」（平均8.5位）
  「参政党 得票率」（8位）だった。今の題名は「比例代表の得票率（政党名）」の順で、探す人が打つ「政党名 得票率」の順になっていない。
